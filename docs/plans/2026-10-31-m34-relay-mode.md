# M34 — Relay mode: big jobs as a chain of short sessions

Status: planned

## The problem

Long tasks are where dcode-ai (and every agent CLI) gets expensive and
unreliable. One conversation carries everything: each step re-sends a
growing history, the context fills, compaction summarizes (and loses
detail), and on the Claude Code backend every rewrite restarts the process
and re-caches the prompt. The Jira/Power Automate session that ran 300+
steps is the typical case.

Other CLIs work inside one context (Claude Code's todo list, Codex's plan,
Gemini's checkpoints). None of them split a job into fresh, small sessions
that hand work to each other.

## The idea

`/relay <goal>` (or `dcode-ai relay "<goal>"`) runs a job as a relay race:

1. **Plan leg** (main model): explore and write `.dcode-ai/relay/<id>/plan.md`,
   a numbered list of legs. Each leg has a goal, the files it touches, and a
   **done check**: a command (`cargo test -p x`, `npm run lint`) or a
   concrete thing to verify. The user approves or edits the plan.
2. **Each leg** runs in a **fresh session** with a small context: the
   system prompt, the plan, the previous leg's **baton** (handoff note), and
   its own goal. No history from earlier legs.
3. A leg ends when its done check passes. The leg writes the baton: what
   changed (files, decisions, gotchas, what's left), at most ~1.5k tokens.
   Then dcode-ai makes a git checkpoint (commit on a relay branch, or a
   stash-style snapshot outside git).
4. **If a check fails**, the leg retries once with the failure output. After
   that it stops and asks the user, showing the leg's log.
5. **At the end**: a short report (legs, checks, commits, tokens per leg),
   and the branch to merge or the diff to review.

## Why it's different

| | One long session | Relay |
|---|---|---|
| Prompt per step | grows to 100–150k | stays ~15–30k (fresh leg + baton) |
| Compaction | repeatedly, lossy | never needed |
| Claude process restarts | on every rewrite | once per leg, small prompt |
| Progress if it crashes | last checkpoint of one session | every finished leg is committed |
| Verification | at the end, if asked | every leg has a done check |
| Resuming | the whole conversation | `dcode-ai relay resume <id>`: next leg from the plan file |

Legs can use different models: the plan and hard legs on the main model,
mechanical legs (renames, test fixes) on the utility model. Independent
legs (marked in the plan) can run in parallel worktrees, reusing sub-agent
isolation.

## Design

- `RelayRun { id, goal, plan_path, legs: Vec<Leg>, branch, status }`, saved
  as `.dcode-ai/relay/<id>/state.json` next to `plan.md` and
  `baton-<n>.md`.
- `Leg { n, goal, files, check, model: Option<String>, parallel_group,
  status, session_id, tokens, attempts }`.
- Plan format: Markdown with a fenced YAML block per leg, so it's readable,
  editable, and parsed strictly. The plan leg is asked for exactly this.
- Leg session: `spawn_child_session` with `use_worktree` per the run (one
  relay branch; parallel legs get their own worktrees, then merge), the
  parent's permission mode, and a system addition: "You are leg n of a
  relay. Do only this leg. When done, write the baton with
  `relay_handoff`."
- New tool `relay_handoff { summary, changed_files, notes_for_next }` (only
  inside a leg): writes the baton and ends the leg.
- Done check: run with the shell tool's sandbox and timeout. Exit code 0 =
  pass. A "manual" check pauses for the user.
- UI: the dashboard's agents tab shows the relay as a lane (legs ✓ / ◐ /
  ✗, tokens); the transcript shows one line per leg plus the baton on
  expand. `/relay status`, `/relay pause|resume|stop`, `/relay plan` (open
  `plan.md` in `$EDITOR`).
- Budgets: per-leg token cap (default 400k), whole-run cap; the burn alarm
  applies per leg.
- Works with both providers; with the Claude Code backend each leg is one
  short `claude` process.

## Phases

1. Plan leg + `plan.md` format + approval (no execution): useful alone.
2. Sequential legs: fresh session, baton tool, done check, git checkpoint,
   retry once, stop-and-ask.
3. Resume after a crash or quit; `/relay status|pause|resume|stop`;
   dashboard lane.
4. Per-leg models; parallel legs in worktrees.
5. End-to-end test with the mock model: a three-leg job (create a file,
   edit it, make a check pass), a failing check that retries and then asks,
   resume after a kill.

## Risks

- Bad plans: legs too big or with weak checks. The plan prompt sets limits
  (a leg should fit in ~30 tool steps; every leg needs a runnable check),
  and the user approves the plan.
- Lost context between legs: the baton plus the plan have to carry it. The
  baton is written by the leg that knows, and the next leg can read files.
- Repos without tests: checks fall back to build/lint, or to "manual".
