# Plan — use the model's full context window (1M) (2026-11-11)

## What's happening today

dcode-ai knows the real windows, then throws them away:

- `crates/runtime/src/model_limits.rs` lists Claude Opus 5.5 / Sonnet 5.5 /
  Haiku 5.5 / Fable 5.x / Opus 4.6+ / Sonnet 4.6+ at **1,000,000**, and the
  background refresh (`model_limits_api.rs`) reads Anthropic's Models API
  `max_input_tokens` (1M for the current models) into
  `~/.dcode-ai/model_limits-v2.json` — which indeed holds
  `Anthropic/claude-opus-5-5: 1000000`, `Copilot/claude-sonnet-5-5: 1000000`.
- Then `working_context_window()` caps every model at
  `DEFAULT_WORKING_WINDOW = 200_000` unless the model id contains `[1m]`
  (added in v1.0.23, copying Claude Code's `sonnet[1m]` convention; the
  reason in the comment: every turn re-reads the whole context, which uses
  up a plan faster).
- `make_context_manager` applies that cap to the footer gauge, `/context`,
  the prune point and the auto-compaction point (~75% → ~150k).
- `[memory.context] context_window_target` can't lift it: it's only read
  when `auto_detect_context_window = false`.
- The `[1m]` escape hatch is half-built: nothing strips `[1m]` from the id
  before the request, so `claude-opus-5-5[1m]` would reach the API as an
  unknown model.
- Copilot: `resolve_model_limits` ignores Copilot's catalog ("no reliable
  per-plan limits") and uses the static table, so for Copilot-served Claude
  it assumes 1M without knowing what Copilot actually accepts.
- Your current default model is `gpt-5.3-codex` on Copilot: its window is
  128k in the table, so the 200k cap isn't even what limits that session.

Per Anthropic's current model docs, Opus 5.5, Sonnet 5.5, Haiku 5.5 and
Fable 5.x all have a 1M window by default (no beta header); only Haiku 4.5
is 200k.

## The trade-off

A bigger window means fewer compactions and nothing forgotten — but every
turn re-sends the whole context. With caching that's cheap per token
(Opus 5.5 cache reads $0.20/MTok: ~$0.15 a turn at 750k) but uncached
turns are expensive (~$3 at 750k on Opus 5.5), turns get slower, and on
the `claude-code` backend (your Claude subscription) a big context uses
plan limits faster. Idle compaction (v1.0.57) already helps here.

## Plan

### 1. One setting for the window
`[memory.context] max_window = "full" | "200k" | <tokens>`:
- `full` — the model's whole window as its provider reports it (1M for
  Claude 5.x). **Proposed default.**
- `200k` — today's behaviour.
- a number — any cap (e.g. `400000`).
It replaces the hard-coded `DEFAULT_WORKING_WINDOW` cap;
`context_window_target` becomes an alias for a number. Per-model override:
`[memory.context.window] "claude-haiku-5-5" = 200000`.

### 2. Switch it in the session
- `/context window full|200k|<n>` for this session; `/context` shows the
  window, where it came from (Models API, Copilot catalog, table) and the
  cap.
- Footer gauge: `ctx 12% · 1M`.
- Model picker: a `1M` badge on models that have it.

### 3. Keep `[1m]` working
Accept `model[1m]` as "full for this model" (Claude Code habit) and **strip
the suffix before every request** — the API, Copilot and the `claude`
binary each get the plain id (or the form that binary expects; check what
the installed `claude --model` accepts for 1M).

### 4. Read real limits per provider
- Anthropic API (`backend = "api"`): already reads `max_input_tokens` —
  use it as-is once the cap is gone.
- Copilot: read `capabilities.limits.max_prompt_tokens` (and
  `max_context_window_tokens`) from Copilot's `/models` catalog for the
  signed-in plan; cap to it. Verify against the live catalog for
  `claude-sonnet-5-5`, `claude-opus-5-5`, `gpt-5.3-codex` first — Copilot
  may serve Claude with a smaller prompt limit than Anthropic does.
- `claude-code` backend: the window is whatever the `claude` binary runs
  with; follow its model choice and report it.
- An over-limit error from any provider → existing overflow path compacts
  and retries, and the learned limit is saved to `model_limits-v2.json`.

### 5. Compaction scaled to the window
- Auto-compaction stays a percentage (~75–85%), so at 1M it moves to
  ~750k; prune point scales the same way.
- Add an optional *soft* budget, `compact_at_tokens` (e.g. 400k), for
  people who want 1M available but compaction earlier to keep turns cheap.
- The summary request must fit: when the history to summarize is bigger
  than the summarizer's own window, summarize in chunks.
- Idle compaction thresholds unchanged (40k min).

### 6. Tests
- `working_context_window` → new `effective_window(model, provider,
  setting)`: full / 200k / number / per-model / `[1m]` cases.
- `[1m]` stripped from outgoing requests (all three backends).
- Copilot catalog parsing from a fixture; cap applied.
- Budget: compact/prune points at 1M and with `compact_at_tokens`.
- Config: old `context_window_target` still honoured.

## Rollout
Release note says the default changed and how to go back
(`max_window = "200k"`). Footer shows the window so the change is visible.

## Decision (2026-11-11): soft 160k budget, full window as the ceiling

Chosen for the lowest credit use without the hard wall:

- **Ceiling = the model's full window** (`max_window = "full"` default): a
  huge file, log or diff no longer forces an emergency compaction (itself
  a paid request) mid-task; the gauge shows the real window.
- **Soft budget `compact_at_tokens = 160_000` by default**: normal
  compaction happens where it does today (~150k), so a turn re-sends at
  most ~200k and credit use stays where it is.
- **Inside a tool loop** the context may run past the soft budget, up to
  `turn_headroom_tokens = 400_000`, instead of compacting mid-work; it is
  compacted at the end of the turn, or by idle compaction while the cache
  is still warm.
- **`/context window full`** lifts the soft budget for one session (big
  refactors, long debugging); `/context window 200k` brings it back.
- Keep the prompt prefix stable so re-sent context bills at cache-read
  price; `/context` shows the cache hit rate.

Rejected: always 1M (each turn re-sends up to ~750k — fastest plan/credit
burn, slower turns); hard 200k (today — big inputs hit the wall, and the
forced compactions cost requests and lose work).
